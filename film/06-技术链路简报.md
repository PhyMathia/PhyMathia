# 技术链路简报（实测）
## 纯代码生成这部片子的工程可行性

> 本机实测环境：Ubuntu 24.04 / Node 22.23.2 / Playwright Chromium 1243 / three r186.1 / ffmpeg 6.1.1 / 24 核 15 GB
> 凡未实测处已明确标注「**待验证**」。

---

## 〇 · 总判断

**全链可行。唯一硬门槛是 headless Chromium 必须真吃到 GPU。**

本机实测（沙箱禁 `/dev/dri`，只能回退 SwiftShader）**3840×1600 每帧**：

| 渲染内容 | 单帧耗时 |
|---|---|
| 单 pass | 19 ms |
| 10 pass 后处理链 | 2.4 s |
| 32 步 raymarch（星云/体积光） | 10.1 s |
| 64 步 raymarch | 26 s |

**5760 帧（4 分钟 24 fps）软渲 = 4–16 小时。真 GPU 通常快 10–100 倍（待验证）。**

> **对本片的直接含义**：镜 36/38 的"海面 + 体积雾"与镜 40 的书法地形都是重负载。**软渲下必须降步数或半分辨率升采样，否则单是第四乐章就要渲一整天。**

## 一 · 离线渲染管线

### 启动参数（实测）

```js
chromium.launch({
  headless: true,
  channel: 'chromium',              // 必须！headless-shell 更弱
  args: ['--use-gl=angle', '--use-angle=vulkan',
         '--enable-unsafe-swiftshader',
         '--disable-dev-shm-usage']  // Linux 专用
})
```

- **自检**：读 `UNMASKED_RENDERER_WEBGL`。出现 `SwiftShader` 就是**没吃到 GPU**，必须断言失败并停止，否则会静默软渲 16 小时。
- Windows 换 `--use-angle=d3d11`。
- **真 GPU 路径本机未能实测**（`/dev/dri` 被沙箱拒 + NVIDIA NVML 报错，Vulkan 只枚举到 llvmpipe）。换有 GPU 权限的机器后，用上面的自检字符串 5 秒内即可确认。

### 抓帧三条路（4K 实测）

| 方式 | 耗时 | 备注 |
|---|---|---|
| `readPixels` | 25–35 ms | **最快，推荐** |
| `canvas.toDataURL('image/png')` | 60–125 ms | 产出 2.9–3.2 MB |
| `page.screenshot` | 38–48 ms | **只截 viewport**——viewport 800×400 时两种不同尺寸的 canvas 都产出 1849 字节的 800×400 PNG。要用必须把 viewport 设成 canvas 尺寸，或用 `elementHandle.screenshot()` |

### ⚠️ 确定性：本项目最大的工程风险（实测）

- 纯不透明单 pass：**跨进程 hash 完全一致** ✅
- **「透明粒子 + Bloom/Bokeh 链」：同一帧连渲三次得到三个不同 hash，且帧内容依赖渲染历史**（先渲 B 再渲 A，A 的 hash 也会变），`renderer.clear()` 无效 ❌

**这对本片是致命的**：全片大量使用透明粒子（星尘、光点、节点辉光）+ UnrealBloomPass。

**必须采取的闸门**：
1. 长渲前先跑「同帧重渲 3 次比 hash」脚本。
2. 不一致则逐 pass 二分定位（先关后处理、再关透明）。
3. 定位后再启动 5760 帧长渲——**否则会得到一批无法复现、无法断点续渲的帧**。

**已知污染源**：`SSAOPass` / `GlitchPass` 源码内使用 `Math.random()`，用前必须打桩。

### 计时陷阱

`drawArrays` 返回的 1.5 ms 是假的（异步排队）。只有 `gl.finish()` + `readPixels` 同步后的数才算真实帧时。

### 替代路线（均不如 Playwright）

- `gl@3.0.7`（headless-gl）：需 node-gyp，WebGL2 覆盖不全
- `node-canvas-webgl`：已陈旧
- Deno WebGPU：同样卡驱动

## 二 · Three.js 能力边界（r186.1，实测可跑）

**后处理链齐备**：`EffectComposer` / `RenderPass` / `UnrealBloomPass` / `BokehPass` / `LUTPass`（调色）/ `FilmPass`（颗粒）/ `ShaderPass`（色差）/ `OutputPass` / `GTAOPass` / `SMAAPass`。

**色彩管理**（r152+ 写法，别再写 `outputEncoding`）：
```js
renderer.outputColorSpace = THREE.SRGBColorSpace;
renderer.toneMapping = THREE.ACESFilmicToneMapping;
```

**抗锯齿**：走累积采样（`SSAARenderPass` / `TAARenderPass`）。**离线渲染正好用多帧累积换画质，成本线性叠加。**

**体积光 / 星云**：raymarch + 蓝噪抖动。代价就是上面的 10–26 s/帧。

**粒子规模**：百万粒子走 GPGPU FBO（位置存浮点纹理，参考 `webgl_gpgpu_birds`）。本机 20 万 Points + 后处理稳定；**百万级待验证**。

> **对本片的直接含义**：镜 53 的"粒子成字"每个字约 2000 粒子，全片约 2 万粒子——**远在安全区内**。镜 36 的大陆（成千上万节点）建议用 instancing 而非独立 mesh；镜 04/09 的八条正弦与八根齿是解析几何，不吃粒子预算。

## 三 · 代码作曲

**首选**：`node-web-audio-api@2.2.0` 的 `OfflineAudioContext`。
实测：5 秒立体声 48 kHz 渲染耗时 301 ms（**16.6× 实时**）。自写 44 字节头存 24-bit WAV。

- **混响**：`ConvolverNode` + 代码生成 IR（指数衰减噪声 + 早期反射）
- **母带**：Biquad EQ → `DynamicsCompressor` → 第二级压限 → `WaveShaper`(tanh)。实测峰值 2.9 被压回不削顶。

**要"像管弦乐"，采样 + 音序远胜纯合成。** 免费可用素材：

| 库 | 许可 | 体积 | 采样率 |
|---|---|---|---|
| Sonatina Symphonic Orchestra | CC Sampling Plus 1.0 | 1.39 GB | **44.1 kHz** ⚠️ |
| VSCO 2 CE | CC0 | — | — |
| FluidR3 GM | Debian 包（MIT 式） | — | — |

> ⚠️ **44.1 kHz 素材混进 48 kHz 时间线必须显式重采样**，否则音画漂移。

**纯合成路线**（FM 铜管 + 失谐锯齿弦乐群 + 包络）本机已出可用的电影感和弦进行——**若坚持"每一个音符都由代码合成"的字面要求，走这条**。

## 四 · 自动剪辑（命令实测通过）

```bash
ffmpeg -framerate 24 -i f%05d.png -i cue.wav \
  -c:v libx264 -crf 12 -pix_fmt yuv420p \
  -colorspace bt709 -color_primaries bt709 -color_trc bt709 \
  -c:a aac -b:a 256k -ar 48000 -movflags +faststart out.mp4
```

实测 12 帧 = 0.5 s，**音视频时长精确相等**。

**中间态（无损）**：`prores_ks -profile:v 3 -pix_fmt yuv422p10le`（实测通过）

### ⚠️ 分辨率必须偶数

**`3840×1607` + `yuv420p` 被 libx264 直接拒绝**（`yuv444p` 可，但兼容性差）。
2.39:1 的精确高度是 1606.7 → **本片取 3840×1608**（偶数，且比 1600 更接近 2.39:1）。

### 音画对齐

**全链 48 kHz**：`48000 / 24 = 2000` 样本/帧，整除。
**44.1 kHz 是 1837.5 样本/帧，必然漂移** —— 这是本片音频链路的硬约束。

**帧号是唯一时间源**：各乐章独立渲序列，再 `concat`。

### 字幕两种做法

| 做法 | 优点 | 缺点 |
|---|---|---|
| **渲进画面**（等 `document.fonts.ready`） | 所见即所得，可用任意 shader 效果（如星尘粒子构成文字） | 改字要重渲 |
| **后期叠加** `-vf "ass=card.ass:fontsdir=..."` | 可改可重排，实测中英双行烧录成功 | 无法做粒子化文字 |

> **对本片的直接含义**：T01–T09 用**后期 ASS 叠加**（可改）；**片头 DEEPSEEK 与 T10 主标题必须渲进画面**（它们由粒子/折射构成，不是平面文字）。

## 五 · 必踩坑清单（10 条）

| # | 坑 | 规避 |
|---|---|---|
| 1 | 静默回退软渲 | **断言 `UNMASKED_RENDERER_WEBGL` 字符串** |
| 2 | `page.screenshot` 只截 viewport | 对齐尺寸或 `elementHandle.screenshot()` |
| 3 | 透明 + 后处理帧内容随历史变 | 建 hash 闸门 |
| 4 | `Math.random()` 藏在 SSAOPass/GlitchPass | 打桩 |
| 5 | `preserveDrawingBuffer:false` 抓到空帧 | 渲完同任务内立刻抓，或开 `true` |
| 6 | 5760 帧 4K PNG 约 **50–70 GB** | 直落盘，别攒内存 |
| 7 | 长渲上下文丢失 / OOM | 每 N 帧重载页面 + 监听 `webglcontextlost` |
| 8 | PNG 全范围 vs yuv420p limited → 发灰 | **显式打色彩标签**（见上方命令） |
| 9 | 每帧新建 RenderTarget → 显存泄漏 | 盯 `renderer.info.memory` |
| 10 | canvas 读回是未预乘 alpha，合成出白边 | 直接 `alpha:false` 不透明输出 |

## 六 · 落地顺序建议

1. **先验证真 GPU**（`UNMASKED_RENDERER_WEBGL` 断言）——这决定整部片子的渲染预算。
2. **再建确定性闸门**（同帧重渲 3 次比 hash）——这决定帧能不能复现与续渲。
3. **然后做 5 个 P0 镜头**（镜 04 / 09 / 31 / 45 / 50，见 `02-分镜表.md` 第六节）——这决定片子能不能成立。
4. 三者都过了，再启动全面生产。

**顺序不能颠倒。** 反过来做，会在第 3000 帧发现自己渲了一批不可复现的帧。
